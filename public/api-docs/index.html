Build on ÒsánVault.

Use the existing platform APIs to integrate asset intelligence, organization workflows and user experiences. This guide separates individual access from organization/tenant access and does not expose secrets or internal database structures.

Quick start

The API is served from the same production origin as the platform. Use relative paths in browser applications and the production origin in server integrations.

const API = window.__HATCHABLE__?.api || '/api'; const response = await fetch(API + '/account/me'); const data = await response.json();
Use the platform-managed authentication flow. Do not create a second login system, password store or users table.

Authentication

ÒsánVault uses the platform's authenticated user session. Protected user endpoints reject anonymous requests. Organization endpoints must additionally enforce the caller's organization membership and role.

Browser

const r = await fetch('/api/account/me', { credentials: 'include' }); if (r.status === 401) { // send the user to the platform sign-in flow } const me = await r.json();

Server-to-server

Use an approved integration credential mechanism when one has been provisioned for your organization. Never place private credentials in browser JavaScript, public HTML, logs or query strings.

Individual API

For a signed-in individual, use the user identity endpoint and the individual-facing product APIs. The platform determines the authenticated identity; clients should not submit a user ID to impersonate another user.

GET/api/account/me
Purpose

Return the authenticated account context and applicable founder/organization reconciliation state.

const r = await fetch('/api/account/me', {credentials:'include'}); const me = await r.json();
GET/api/employee/me
Purpose

Return the authenticated employee's self-service record when the account is legitimately linked to an employee record.

const r = await fetch('/api/employee/me', {credentials:'include'}); const employee = await r.json();
An authenticated account is not automatically an employee, director, shareholder, beneficial owner or organization administrator. Those relationships require their own verified records.

Organization API

Organization APIs operate in a tenant context. A legitimate organization membership should determine what records the caller can see or change. Never trust an organization ID supplied by an untrusted client as proof of membership.

GET/api/organizations/me
Purpose

Return the authenticated user's organization context where a legitimate organization relationship exists.

const r = await fetch('/api/organizations/me', {credentials:'include'}); const organization = await r.json();
GET/api/organizations/dashboard
Purpose

Retrieve the organization dashboard data available to the authenticated organization context.

const r = await fetch('/api/organizations/dashboard', {credentials:'include'}); const dashboard = await r.json();
GET/api/workforce/overview
Purpose

Retrieve workforce overview data for the authorized organization workspace.

Tenant rules

RuleRequired behavior
IsolationOnly return records belonging to the authorized organization context.
AuthorizationCheck role/permission server-side before mutations or sensitive reads.
IdentityDerive caller identity from the authenticated session, not request fields.
EvidenceKeep source, verification and provenance separate from business assertions.

Asset API patterns

Asset integrations should treat the canonical asset registry as the source of asset identity and keep verification, evidence, valuation and investment readiness as separate states.

GET/api/assets/:id
Purpose

Retrieve an individual asset record and its linked project, valuation and risk context where permitted.

GET/api/governance/assets
Purpose

Read the continental asset-intelligence registry used by the governance workspace.

Never convert a claimed owner, inferred location, uploaded document or unverified valuation into a verified production fact. The platform is intentionally fail-closed.

Responses & errors

Clients should handle HTTP status codes explicitly.

StatusMeaningClient action
200Request succeeded.Use the returned data.
400Invalid request.Correct the request; do not retry unchanged.
401Authentication required.Sign in or refresh the authenticated session.
403Authenticated but not authorized.Request the appropriate organization role/permission.
404Resource does not exist or is not exposed.Check the identifier and endpoint.
409State conflict.Resolve the business-state conflict before retrying.
500Server error.Retry cautiously and report the request context without sending secrets.

Security & integration rules

  • Use HTTPS in production.
  • Keep credentials server-side.
  • Use least privilege and organization-scoped permissions.
  • Do not put secrets in URLs or logs.
  • Validate all input server-side.
  • Use pagination/filtering for large collections.
  • Record request IDs and audit-relevant events for sensitive operations.
  • Do not build a second authentication or tenant system around ÒsánVault.
For production integrations, use a versioned API contract and an OpenAPI specification as the contract between ÒsánVault and external clients.
